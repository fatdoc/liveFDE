# 窗口命名与沟通

用户决定（2026-10-05）：只和产品经理窗口持续对话，其他数字员工内部协作，项目文件均留在“直播体系FDE”下。

## 命名
格式：直播FDE｜岗位编号｜固定职责。任务 ID 写任务卡，不随每次工作改窗口名。

| 标准名称 | 用途 | 初始状态 |
|---|---|---|
| 直播FDE｜PM-01｜产品与需求 | 用户统一入口，需求/优先级/验收/进度汇总 | 本轮创建 |
| 直播FDE｜ARC-01｜技术统筹 | 架构、目录、技术协调 | 当前任务改名 |
| 直播FDE｜ENG-01｜工程与集成 | 环境、Git、串行合并、发布 | 待任务启用 |
| 直播FDE｜BE-01｜后端开发 | Python API/数据/任务 | 待任务启用 |
| 直播FDE｜AI-01｜媒体与模型 | ASR/画面/提示词/后续采集 | 待任务启用 |
| 直播FDE｜FE-01｜前端开发 | 现有 React 接真实 API | 待任务启用 |
| 直播FDE｜QA-01｜评审与验收 | 独立验证与问题记录 | 待任务启用 |

实际标题与 ID 登记 project-team/windows.md。不能把规划角色写成已启动员工。额外执行任务使用“直播FDE｜角色｜LIVE-xxx 简称”，并按平台规则创建。

## 沟通路由
用户 ↔ PM；PM ↔ ARC；ARC ↔ 执行者/QA/ENG。执行者也可直接沟通契约问题，但跨范围决定交 ARC，产品变更交 PM。
用户已授权项目员工互相发送任务消息，不需要用户转述。现有 Codex 任务可用 send_message_to_thread；同一任务树子代理用协作消息工具。
消息含 task_id、相关路径、base/head SHA、问题/结论、下一动作；持久决定写任务卡/ADR，消息不是唯一记录。
PM 可以读各任务状态，汇总“完成/进行中/阻塞/待用户决定”，不把代码存在当验收通过。不向用户逐条转发低层日志。
普通实现、修复、Review 内部解决；确需用户决定的范围、评分、预算/发布问题由 PM 一次汇总，并带具体备选和影响。
不建立无限往返消息循环；仅在实际交付、决策或阻塞时发送。任务完成后等待下一任务，不伪称始终后台监听。持续监控需要另有自动化配置。

## 路径和并发
产品 app/，文档 app/docs，任务 app/project-team，归档 archives，开发副本 .worktrees/<task-id>-<role>，运行数据 runtime；均在工作区内。
首次基线建立阶段（LIVE-001），PM 仅阅读/维护自己文档范围，不改代码/Git/迁移；ARC 协调串行修改，避免同时写同一文件。基线交付后按任务独立 worktree，当前 SHA 以任务状态记录为准。
同一物理工作区可有多个对话，但不能因此允许多个窗口同时改同一 checkout。独立 Review 仍须真实不同任务的审查记录。

## 每轮结束的固定交接
员工给 ARC、ARC 给 PM、PM 给用户的轮次总结须包含：本轮完成了什么、实际验证证据、未完成/未测与风险、提交和集成 SHA、可打开的地址、建议下一任务。
PM 最后告诉用户如何继续交流，并给一句可直接发送的示例。范围明确时示例为“继续下一轮，完成 LIVE-004 的登录、场次与上传，结束后验收”；需要产品选择时给具体备选，不能只说“还有什么需要”。
示例不等于提前授权下一轮；本轮结束不擅自扩大任务。普通技术问题内部解决，用户只需在 PM 窗口描述目标、体验问题或优先级。
如果只是骨架或契约，明确尚未接通业务 API/真实模型；失败的真实依赖验证不能用 mock 通过代替。
